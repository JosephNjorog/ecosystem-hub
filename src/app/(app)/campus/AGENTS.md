# Campus

Rules for this area. The root `AGENTS.md` applies too.

## Today (`src/app/(app)/campus/` - no public routes yet; admin `/admin/campus`)
- **Pick-lists** = `Organization` (`prisma/schema/organizations.prisma` - shared, other areas will use it too; deleting a university with clubs is refused, merge moves them), `type` `university` | `blockchain_club` (same ids as the member-portal CRM, for a later join; a club's `parentId` is its university). An `Organization` exists only once somebody uses it - universities come from the catalog below or are typed in, clubs are typed in. **No CRM import**: the hub doesn't read universities or clubs from the member portal (removed on purpose - the catalog covers universities); the CRM can join later on `rorId`.
- **University catalog** = `UniversityCatalog`: the OpenAlex snapshot (education institutions with a ROR id, ~30k, CC0), replaced as a whole by a manual import about once a year (a local script, not in the repo: public S3 bucket over HTTPS, `searchText` = `normalizeOrgName` of name + `cleanAliases`). Empty catalog = the picker only finds typed-in entries. A reference list only - **no `Organization` per catalog row**. The university picker searches **on the server** as you type, so everybody sees the same list no matter who picked what before (`searchUniversities` in `src/lib/organization-actions.ts` -> `searchUniversities` in `src/lib/organizations.ts`: every word must match - catalog rows by `searchText`, biggest by `worksCount` first, as their `Organization` id when one is linked (hidden ones left out), else `CATALOG_VALUE` + rorId; then visible Organizations matching their own name or alternative names (typed-in ones, admin renames and aliases); a typed-in twin of a catalog hit, same name and country, stays out - merged by the pure, tested `mergeUniversityHits` in `src/lib/campus.ts`; the form shows a result only for the query it answers). The form only gets the user's own universities and all clubs (`getOrgOptions`). An `Organization` is created when someone saves a catalog pick (`catalogUniversity` in the form, `findOrCreateCatalogOrg`): the one linked to that `rorId`, else it claims a visible unlinked same-name university in the same country (a typed-in twin; gets `rorId`, `verified`, the catalog's names as aliases, audited `organization.ror_link`), else a new verified one (`createMany` + `skipDuplicates`, so two first picks at once don't fail). Name and country always come from the catalog row, never the client. `Organization.rorId` (unique) is the shared key with the catalog and, later, the CRM. The member portal loads the same snapshot itself - the catalog is never synced between hub and portal.
- **Typed-in additions**: a builder who can't find their university/club types it; `saveProfile` creates it unverified via `findOrCreateOrg` (`src/lib/organizations.ts`: reuses a same-name entry incl. hidden ones; `assertOrgQuota` = `MAX_NEW_ORGS_PER_DAY`, counted inside the transaction so only real creates count; hidden ones can't be picked unless already the user's own; a club not under the chosen university is dropped). They show up in everybody's search right away. Admins (`campus.manage`) verify, rename, hide or **merge** them at `/admin/campus/organizations` - merge moves members, club members and clubs, carries the `rorId` (two different `rorId`s can't be merged), keeps the source's names as alternative names, deletes the source.
- **Alternative names** (`aliases` + `normalizedAliases`, `cleanAliases` in `src/lib/campus.ts`): "Universität Wien" for "University of Vienna". Admin-maintained; catalog picks start with the catalog's names. The pickers search them, and every same-name check (`orgNameMatch`: `findOrCreateOrg`, admin search) treats them like the name, so a typed-in alias reuses the entry instead of adding a duplicate.
- **Membership** = `UniversityMembership` (several per user, `@@id([userId, universityId])`, indexed by university - "students of X" is the future campus feed). `kind` student | faculty | staff (self-chosen). Student-only fields: `fieldOfStudy` (required; `FIELDS_OF_STUDY` + free "Other"), `graduationYear`, club + position. Per person in `CampusProfile` (1:1 with `User`, created on the first save as a student): `trackInterests`, `campusCoordinatorInterest`, `adultConfirmedAt` (students confirm 18+; set once, kept). Rules + form checks in `src/lib/campus.ts` (pure, tested in `tests/campus.test.ts`), zod in the profile's `schemas.ts`. Dropping the University role deletes the memberships on save.
- Where code lives: pickers + org rules are **core** (`src/lib/campus.ts`, `src/lib/organizations.ts`, `src/lib/organization-actions.ts`, `SearchSelect`'s `onCreate` / `onSearchChange` / `emptyText`) because the profile and the admin both need them; the profile form part is `profile/_components/university-fields.tsx`; this area owns permissions and the admin actions.
- Permissions: `campus.view` (sensitive - students' emails, Telegram, study data; `/admin/campus`), `campus.manage` (the lists).

## Later (planned, iterate with the program team)
- Campus coordinators = **per-object power** (`UniversityCoordinator` table + `canCoordinate(user, university)`), not a permission - they see their university's students.
- Students finding each other per university, projects together (a builder social network). Students are 18+.
- The CRM joins on `rorId`: the portal stores it on `CrmOrganization` (picked from its own copy of the snapshot) and reads the hub's universities/members per `rorId` from the hub's `/api/v1` (the hub stays read-only towards the portal).
- Hub-added universities back to the CRM: the portal reads them from the hub's `/api/v1` and files `CrmSuggestion`s.
